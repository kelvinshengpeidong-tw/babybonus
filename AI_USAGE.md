# AI Usage

This document explains how AI was used during the development of this project:
- What AI tools were used
- What they were used for
- How AI generated outputs were reviewed and validated
- Cases where AI generated code or suggestions were discarded

---

## AI Tools Used

- Cline (Claude Code)
- ChatGPT
- Google AI (AI Overviews in Google Search Engine)

---

## What They Were Used For

- Planning & architecture discussions (ChatGPT)


- Kotlin syntax help coming from Java background (ChatGPT, Google AI)


- Loading JSON files utility (ChatGPT, Google AI)


- Discussing trade-offs between different approaches towards a problem (ChatGPT, Cline, Google AI)


- Debugging errors in code (Cline, ChatGPT, Google AI)


- Reviewing code to identify any issues that I might have been missed (Cline)


- Reviewing test coverage for any missing cases that were not covered (Cline)


- Drafting README content/curl examples (Cline)

## How Outputs Were Reviewed and Validated

- For Cline, I only used `Plan` mode as it is easier for me to review the AI suggested code. Only after understanding its code line by line will I 
take what I need. Using `Plan` mode also ensures that the AI does not make its own changes to my code which typically seems to be a lot


- If I do not understand the reasoning behind the AI suggestion, I will ask it to provide its reasoning or elaborate more. Sometimes, 
I know the AI suggestion is incorrect, so I will provide my own suggestion to challenge what the AI say, and it will say it made a mistake


- Cross-reference the code or suggestion generated by one AI tool with another, or search up the unfamiliar syntax in Google
  - If the AI response did not seem right, or I did not understand its suggested code change, I will google its terms (e.g. inline + reified)


- When I think the solution provided is not the best and there can be a better alternative, I will do a back and forth suggestion with the AI to discuss 
the trade-offs for each approach

## Cases Where AI Generated Code/Suggestions Were Discarded

- Discussion with AI on the project planning and architecture, whether to package the files/classes via layer or features
  - Package by Layer, e.g. domain, repository, dto, service, controller etc.
    - Advantage: Can find all the layer information in each folder
    
    - Disadvantage: To understand a feature, need to look in all folders

  - Package by Feature, e.g. Enrollment, Disbursement, IcaClient, IroasClient etc.
    - Advantage: Can find all the related information of a feature in 1 folder, so easy to understand each business capability
    
    - Disadvantage: If we want to understand a single layer, we will need to look through all the folders (e.g. To know all the API endpoints that are present)

    - Final decision: Decided to combine both approaches. At the topmost layer, we package by feature. Then in each feature folder, we package by layer. So 
      that when project grows with more features, it looks more organized and easier to find the information for a feature in one folder. Also, even within 
      the feature folder, it will still be easy to check what each layer for this feature does


- Discussion with AI on whether the `maskNric` method in DataMasker class should normalize and validate the NRIC input again when the `formatAndValidateNric` 
method already do so in the NricValidator class
  - If yes
    - Advantage: Safeguard. Any service can use this `maskNric` without needing to know if the NRIC is already processed

    - Disadvantage: `maskNric` will be dependent on NricValidator class, so coupling exists between these two classes

  - If no
    - Advantage: Decoupling. Datamasker class will not be coupled with NricValidator class, so each class has only one responsibility

    - Disadvantage: A service may use `maskNric` without calling the `formatAndValidateNric` first which will result in bad processing depending on the given input
    
    - Final decision: I decided to go with the second option to follow the S in SOLID design principles, by only having each class be in charge of one responsibility


- For the JSON file loader method `loadList` in JsonLoaderUtil class, AI suggested using inline + reified approach `inline fun <reified T> loadList(path: String): T` 
to eliminate boilerplate by letting the compiler know the object type at compile time. But I found that this does not work for me as 
my `objectWrapper` field is set to `private`. The keyword `inline` indicates that the entire method will be pasted into the function call 
and this requires the `objectWrapper` to be `public`. There is also the disadvantage of the compiled code size being larger if this inline 
method is used everywhere in the project
  - I prefer to keep class fields `private` if there is no need to expose them to other classes, so I decided to still pass the `Class<T>` 
    explicitly: `fun <T> loadList(resource: String, arrayClass: Class<Array<T>>): List<T>`


- For loading the JSON file in the StubIcaClient and StubIroasClient classes, AI suggested using `@PostConstruct` to load the mock-data from 
the JSON files into the `children`/`parents` field variable. But this will force the `children`/`parents` to be `lateinit var`, making it lose 
its mutability property
  - I prefer to do it in a simpler way which I understand better, by initializing the `children`/`parents` fields the moment they are created: 
    `private val parents: Map<String, Parent> = loadMockData()`. With this approach, the field type remains `val` which allows it to retain its 
    immutable property


- For the EnrollmentServiceTest error cases where child/parent NRIC could not be found, AI suggested that I also check 
that the `enrollmentRepository` is never saved: `verify(enrollmentRepository, never()).save(any())`
  - But we can see that from the `enroll` and `isEligibleForEnrollment` methods that the line `enrollmentRepository.save(enrollment)` 
    will never be reached as exception will already have been thrown before then. Hence, it is not necessary to verify the 
    `enrollmentRepository` is never saved


- For the EnrollmentServiceTest, AI recommend me to test that the NRIC is normalized and validated again even though I already have these tests 
inside the NricValidatorTest
  - I decided not to follow its suggestion as it will just be duplicating the same testing process
